# Безопасность Компаса

Состояние на 23 октября 2026. Это модель угроз и план реализации, не сертификат безопасности и не заключение о соответствии требованиям. Реальные медицинские данные в текущем прототипе не использовать. Актуальная архитектура — ARCHITECTURE.md, отдельный локальный стенд — PRESENTATION.md. Описание интернет-демо ниже относится к замороженной предыдущей версии, а не к публикации текущего MVP.

## 1. Граница текущего результата

Локальный прототип теперь имеет API и PostgreSQL в Docker. Сохранённые дневники, настроение, сон, ответы и результаты шкал, дневные статусы демопрепаратов переживают перезагрузку страницы и перезапуск контейнеров. Основной экземпляр доступен только через 127.0.0.1:4174; PostgreSQL не публикуется на хост.

По отдельному прямому запросу пользователя запущен изолированный стенд для коллег: собственные база, volume и ключи, код входа и временная HTTPS-ссылка. Его шлюз публикует только loopback 4175 для диагностики, API/БД внешних портов не имеют. TLS WebSocket-туннель работает в Docker; маршрутизация идёт только к демошлюзу. Первичные локальные записи туда не копировались. Это тестирование интерфейса на вымышленных данных, а не допуск медицинского сервиса.

HTTPS завершается у Tunnelmole: оператор туннеля технически может видеть передаваемый тестовый HTTP-трафик после расшифрования; до компьютера идёт отдельное TLS WebSocket-соединение. Код доступа не превращает этот маршрут в допустимый канал для реальных медицинских данных. Используется небольшой адаптер [публичного протокола клиента](https://github.com/robbie-cahill/tunnelmole-client), без установки SDK, его аналитики и логирования запросов. Личные SSH-ключи не используются.

Использовать только вымышленные данные. Локальная регистрация и вход по паролю, фиксированные роли и технические согласия добавлены; email и квалификация врача не проверяются. Нет восстановления пароля, MFA, clinical monitoring, юридической проверки согласий или аттестации. Cookie действует 30 дней. Старый профиль без регистрации остаётся отдельным от нового аккаунта, без автоматического переноса медицинских записей. Это не замена идентификации медицинского сервиса.

## 2. Реализованные ограничения

| Мера | Реализация | Граница гарантии |
|---|---|---|
| Передача | Только API того же origin; внешних трекеров/LLM нет | Web-контейнер имеет edge-сеть, полный egress deny не реализован |
| Браузер | Нет browser storage для медицинских данных, HTML-инъекций и eval | Чужие расширения, ОС и XSS при будущих изменениях вне этой гарантии |
| Сессия | Случайный 256-bit token, в БД только SHA-256 hash, HttpOnly/SameSite=Strict cookie; новый token/CSRF при входе | Основной loopback HTTP без Secure; интернет-демо использует Secure. Email/личность/квалификация не верифицированы |
| CSRF | Точный Origin/Host, SameSite, CSRF-токен мутаций, нет CORS-разрешений | Не защищает от вредоносного кода, уже исполняющегося в том же origin |
| Авторизация | ID и фиксированная роль берутся из сессии; активная связь, согласия, объектные проверки и RLS | Регистрация роли врача не подтверждает квалификацию; исследовательский гостевой путь остаётся отдельным |
| RLS | FORCE RLS для patient_entries/patient_doses; non-owner/non-superuser runtime role; транзакционный контекст | БД-роль API доверенная; приложение обязано правильно выбирать профиль из сессии |
| Шифрование | AES-256-GCM для содержимого записей/ответов, IV и tag, AAD связывает профиль и ID | Расшифровывают сервер/worker; это не E2EE. Типы, даты, связи, статусы и signal_level открыты в БД; KMS/ротации пока нет |
| Ключи | Отдельный Docker secret, .local-secrets/0700, исключён из образа | Файловый secret mount Compose не равен зашифрованному secret store; администратор хоста имеет доступ |
| Целостность | Серверная валидация, параметризованный SQL, ревизии заметок/схем/приёмов, квитанции повторов и транзакции; пересечения приёмов защищает БД | Аудит ряда действий есть, общей эксплуатационной системы аудита и клинического реагирования нет |
| Ошибки | Нет ложного успеха при недоступности БД; тексты остаются в форме; лимит тела 100 KB и rate limit | Несохранённые черновики не восстанавливаются после закрытия вкладки |
| Кэш | no-store для персональных API; SW static allowlist; owner-scoped ресурсы в памяти удаляются при смене владельца/отключении | Публичные версионные файлы кешируются по хешу; offline-сохранения медицинских данных нет |
| Заголовки | CSP, frame deny, no-referrer, nosniff, Permissions-Policy | React inline styles разрешены; HTTPS/HSTS нужны в отдельной инфраструктуре |
| Контейнеры | web non-root/read-only/cap_drop ALL; db private network без опубликованного порта | Это не независимый аудит безопасности контейнеров и хоста |
| Логи | Не логируются тела, cookie, токены и тексты; ошибки соединения обобщённые | Производственные аудит и мониторинг ещё не реализованы |

Проверки: unit-тесты шифрования/подмены AAD и серверной валидации; реальный API с двумя синтетическими профилями; RLS проверена именно соединением compass_app (пустой контекст ничего не читает, чужая запись отклоняется, контекст транзакции сбрасывается). Перед выпуском проверки необходимо расширять, а не считать этот список сертификатом.

Демошлюз дополнительно проверяет Host/Origin и HTTPS, не пропускает анонимные запросы к приложению/API, хранит только хеши восьмичасовых пропусков в памяти и не пересылает cookie пропуска в приложение. Есть лимит попыток входа, размера формы, соединений и времени запроса. Общий код защищает приглашённую демонстрацию; это не персональная идентификация и не полноценная защита от DDoS. При перезапуске шлюза код нужно ввести снова. API-cookie демоверсии получает Secure благодаря HTTPS origin. На самой странице входа Referrer-Policy=same-origin нужен для корректного Origin нативного POST; страницы приложения по-прежнему используют no-referrer.

## 3. Что защищаем в рабочем сервисе

- Психоэмоциональные отметки, содержание заметок, сон и ответы на опросники.
- Диагнозы, хронические заболевания, аллергии, препараты и схемы лечения.
- Факт обращения к конкретному врачу, переписку и расписание.
- Идентификаторы пользователей и их связь с медицинскими записями.
- Push-подписки, сессионные cookie, ключи, резервные копии и аудит.

Даже время обращения или название сервиса в уведомлении может раскрывать нежелательную информацию. Доступ к одному пациенту не означает доступ ко всем пациентам или ко всем типам его данных.

## 4. Модель угроз следующего этапа

| Угроза | Сценарий | Предотвращение | Доказательство до запуска |
|---|---|---|---|
| Чужие записи по ID | Пациент меняет patient_id в URL/JSON | Сервер определяет пациента по сессии; объектная авторизация и RLS | Негативные тесты двух пациентов на каждом endpoint |
| Избыточный доступ врача | Врач открывает пациента без активной связи | CareRelationship + срок + согласие, deny by default | Тесты без связи, после её отзыва и истечения |
| Старый врач после смены | UI показывает нового врача, но старый доступ остался | Транзакционный отзыв прав, серверная проверка при каждом чтении | Параллельные запросы до/после перехода и аудит |
| Захват аккаунта врача | Утёк пароль, восстановление или активная сессия | MFA, rate limits, безопасное восстановление и отзыв сессий | Тесты перебора, восстановления, устройств и MFA |
| XSS и утечка сессий | Заметка/сообщение или библиотека исполняет HTML | React escaping, CSP, запрет опасного HTML, HttpOnly cookie | Проверки payloads, CSP и зависимостей |
| CSRF | Другой сайт меняет назначения или согласие | SameSite cookies + CSRF-token/Origin checks, запрет GET-мутаций | Cross-site сценарии с реальными браузерами |
| Утечка из браузерного кэша | Ответ врача/дневник доступен после выхода | no-store персональных API, запрет caching в SW, очистка состояния | Проверка cache/storage/history после выхода и офлайн |
| Утечка из логов | Тексты заметок попадают в access/error analytics | Запрет тела/PII в логах, allowlist полей, редактирование ошибок | Автоматический поиск canary-данных в логах |
| Push на экране блокировки | Название препарата видно окружающим | Нейтральное сообщение, настройки приватности и отзыв согласия | Физический тест заблокированного устройства |
| Ошибочный факт приёма | Повтор запроса создаёт два события | Idempotency key + уникальный DoseEvent + транзакция | Retry/timeout/offline/concurrency тесты |
| Ошибочное назначение | Пациент меняет титрацию или модель предлагает дозу | Раздельные права, подпись авторства, история, подтверждение врача | Тесты пациента, врача и старых версий плана |
| Доступ к бэкапам/БД | Утекла копия или администраторские права | Шифрование, KMS вне БД, узкие IAM-права, аудит | Восстановление из зашифрованной копии с отдельными правами |
| Файл с вредоносным содержимым | Вложение маскируется под анализ | Закрытое хранилище, MIME/magic checks, AV, лимиты, signed URLs | Набор неподдерживаемых/опасных файлов и проверка чужих ссылок |
| LLM-утечка/инъекция | Дневник уходит внешней модели или содержит инструкции | Без внешней отправки по умолчанию, согласованный контур и минимизация, текст как данные | Проверка egress и корпуса атак до включения LLM |
| Неполное удаление | Пользователь удалил запись, но копия осталась у подрядчика | Карта данных, сроки и процедура удаления/backup retention | Полный проход запроса на удаление и журнал исполнения |
| Сбой сервиса | Потеря данных/напоминаний при падении | Бэкапы, recovery drills, retry-очередь, мониторинг, понятные ограничения | Подтверждённые RPO/RTO и тест восстановления |

## 5. Идентификация и доступ

Использовать зрелый компонент идентификации. Не писать собственную криптографию, хранение паролей и токены восстановления с нуля. Разделить пациентские, врачебные и административные полномочия. Поддержка не должна автоматически иметь доступ к содержанию дневников.

Сессию хранить в cookie с Secure, HttpOnly и подходящим SameSite; добавить CSRF-защиту для мутаций. Access/refresh tokens не класть в Web Storage. Для просмотра/экспорта особо чувствительных данных и изменения согласий предусмотреть повторную идентификацию. Врачам и администраторам включить MFA, отзыв активных сессий и проверку восстановления доступа.

Авторизация должна проверяться на сервере для каждого объекта независимо от того, скрыта ли кнопка в интерфейсе. Дополнительная защита PostgreSQL RLS работает под отдельной runtime-ролью, не владельцем таблиц и без BYPASSRLS. Миграции исполняются другой ролью. Нельзя считать RLS включённой только по наличию SQL-файла: нужны тесты реальной роли подключения.

Смена специалиста — операция доступа, а не замена имени в UI. Проверить согласие пациента, старую и новую связь, сроки, атомарность и аудит. Новые данные не должны быть доступны старому врачу из кэша. Юридически необходимое хранение исторической документации отдельно согласовать с ответственными, не обещать мгновенное удаление всех копий.

## 6. Хранение, сеть и ключи

Выбрать допустимые регионы для production, реплик, бэкапов, мониторинга и всех подрядчиков. БД не публиковать в интернет. На внешней границе HTTPS; соединения с отдельными сервисами защищать по соответствующей сети и TLS-политике. HSTS включать только на корректно настроенном HTTPS-домене; пример дан в Caddyfile.example.

Хранение минимальное. Разделить идентификационные и медицинские данные. Шифровать носители и бэкапы; при выбранной модели угроз дополнительно шифровать тексты записей/переписки на уровне приложения, используя KMS/secret manager вне БД. Документировать, кто может расшифровать, как меняются ключи и как восстанавливаются данные. Шифрование без контроля доступа к ключам не решает утечку.

Назначить срок хранения для каждой сущности, включая аудит и push-подписки. Проверить экспорт, исправление, удаление и выбывание данных из резервных копий. Test/stage использовать только с синтетическими записями. Не копировать production-бэкап разработчикам.

## 7. Медицинские функции и сообщения

- Все клинические изменения выполняет авторизованный врач, история сохраняется.
- Данные со слов пациента отмечаются источником; не превращаются автоматически в подтверждённый диагноз.
- PHQ-9 и GAD-7: русские формы, права и подсчёт проверены, источники в ASSESSMENTS.md. Диагноз и лечение автоматически не определяются. Клинический протокол сопровождения ещё не утверждён. Шкала Бека не добавлена без проверки условий.
- Отсутствие записи не равно хорошему состоянию; пропуск данных и ухудшение — разные показатели.
- Проверка совместимости требует проверенного источника и контроля покрытия/версии, а не только списка названий.
- LLM-сводка, если появится, — черновик с цитатами исходных отметок, проверяемый врачом. Никаких автоматических назначений.
- В чате понятные часы ответа и отсутствие обещаний экстренной помощи. Тревожная кнопка требует отдельного клинического процесса и проверенных контактов по региону.
- Push не гарантирует доставку и не должен быть единственным способом контроля лечения. По умолчанию без диагноза, имени препарата и текста переписки.

## 8. Журналирование и инциденты

Писать минимальный аудит доступа: идентификатор исполнителя и объекта, действие, разрешённость, время и request ID. Не писать содержание заметок, диагнозы и токены в application/access логи, URL и сторонние error reporters. Исключить session replay, скриншоты медицинских экранов и выгрузки состояния клиента.

Нужны ограничение доступа к аудиту, контроль целостности и срок хранения. Настроить обнаружение массового чтения, необычных экспортов, перебора и ошибок авторизации. Составить и проверить регламент: кто реагирует, как изолируются сервисы, отзываются ключи/сессии, восстанавливаются данные и выполняются необходимые уведомления.

## 9. Условия допуска к пилоту

1. Подтверждены юрисдикция, оператор, подрядчики, основания, документы и карта потоков данных.
2. Все API имеют аутентификацию, объектную авторизацию и негативные ролевые тесты.
3. Пройдены сценарии смены врача, отзыва согласия, восстановления аккаунта и выхода на общем устройстве.
4. Проверены сетевые границы, секреты, шифрование и реальное восстановление резервных копий.
5. Логи и мониторинг не содержат canary-медицинских записей.
6. PWA не кэширует персональные ответы; privacy-тексты совпадают с фактическим поведением.
7. Клиническая команда утвердила инструменты, назначения, реакции и ограничения.
8. Проведена независимая проверка безопасности; замечания, блокирующие запуск, устранены.

До этого допускаются только вымышленные записи. Конкретные применимые правовые требования должен подтвердить ответственный специалист; этот документ не является правовой консультацией.

- [OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) — ограничения браузерного хранилища для чувствительных данных.
- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) — управление сессиями и очистка клиентских данных.
- [OWASP Web Frontend Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Web_Frontend_Security_Cheat_Sheet.html) — CSP, безопасный вывод и зависимости.
- [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) — минимизация данных и управление ключами.
- [web.dev: установка PWA](https://web.dev/learn/pwa/installation) — различия браузерной и iOS-установки.

Источники сверены в этой итерации. Практическое соответствие подтверждается реализацией и тестами, а не ссылками.

Технические первоисточники этой итерации: [параметризованные запросы node-postgres](https://node-postgres.com/features/queries), [PostgreSQL 17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

Patient and doctor role cookies now use separate names in one browser. `X-Compass-Role` chooses the cookie, not a permission: server capability, active care link, patient consent and row ownership are checked on every operation. A permanent 48-bit patient code locates a pending access request only; it does not disclose the medical profile. Codes/names are stored encrypted (lookup hash separately), and sessions remain cookie-bound local research profiles rather than production identity verification.

Physician reconciliation of current medication/ICD diagnoses is link-authorized, encrypted, revision-checked and audited. Canonical names come from the exact GRLS product or ICD code; client-supplied attribution is ignored. Profile changes invalidate a prior prescription safety fingerprint. Public source ingestion is offline and admin-only; no patient payload is sent to a reference source.


Patient removal of a physician-issued scheme is archive-only: the backend compares the complete normalized configuration, rejects dose/product/source changes and reactivation, preserves physician provenance and every prior version. It only removes future reminders/current-list membership, never deletes the prescription or recorded intakes. A linked physician can archive a current scheme with an optimistic revision and an attributed audit event. Reference product names for manually created plans are canonicalized server-side.

## Локальные аккаунты и согласия, 19 октября 2026

Регистрация создаёт новый случайный principal и изолированный профиль. Вход по email/паролю восстанавливает этот профиль; роль аккаунта неизменна, одинаковый адрес может отдельно использоваться пациентом и врачом. Выбор роли и `X-Compass-Role` выбирают cookie, но не меняют серверные права. Пациентский аккаунт не может включить врачебную роль. Уже открытый анонимный профиль не присваивается аккаунту: сохраняется только отдельная HttpOnly-cookie со старым непрозрачным токеном, которая восстанавливается после выхода.

Пароль длиной 12–128 символов хранится как salted scrypt (`scrypt-v1`, N=32768, r=8, p=3, случайная 128-bit соль), с проверкой через timingSafeEqual. Это встроенная реализация Node, без новой криптографической конструкции. Параметры соответствуют варианту 32 MiB из [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt), сверено 19 октября 2026. Email, имя, фамилия, возраст и согласия шифруются AES-GCM; поиск email использует HMAC с разделением домена. В ответах и логах пароль/токен не возвращаются. Сессия и CSRF обновляются при каждом входе, выход завершает выбранную сессию на сервере.

Вход/регистрация требуют точного Origin, клиентского заголовка и CSRF текущего профиля. Ошибки входа не раскрывают существование адреса; число попыток ограничено по адресу клиента и хешу логина. Лимит хранится в ограниченной памяти процесса и сбрасывается при его перезапуске; распределённого антибот-сервиса и защиты от DDoS нет. Подтверждение email, восстановление пароля, проверка диплома, MFA и выход со всех устройств остаются отдельными задачами.

Согласия сохраняются с версией `compass-local-2026-10-19-v1`, временем и зашифрованной историей событий. На личные записи отдельно запрашиваются обработка и доступ врача; оба флага изначально выключены, доступ требует включённой обработки. Пока доступ выключен, сервер отфильтровывает journal-записи до расшифровки для врача и скрывает старые текстовые mood-заметки. При включении врач получает текст только в активном, отдельно одобренном пациентом подключении. Отзыв закрывает последующие чтения; блокировка строки аккаунта сериализует чтения с отзывом согласия. Никакого внешнего анализа/LLM этот флаг не запускает.

Отзыв основного согласия запрещает новые медицинские изменения и врачебное чтение; пациент сохраняет доступ к собственным уже сохранённым записям и настройкам согласий. Отзыв не равен удалению истории или резервных копий. Эти формы фиксируют техническое решение пользователя в исследовательском прототипе и не объявлены юридически достаточным согласием для клинического сервиса. Внешний замороженный демостенд этой итерацией не обновляется.

## Ограниченная история, 24 октября 2026

История выдаётся по выбранному периоду/странице. Личный список заметок содержит краткий фрагмент, полный текст — в отдельном запросе владельца. Врачебные источники/результаты сохраняют отдельные разрешения и неизменяемые версии. HMAC-курсоры привязаны к владельцу и фильтрам, не содержат текста заметки/поиска; счётчик ревизии и время — технические открытые метаданные. Изменение истории во время перелистывания возвращает явный конфликт. Поиск расшифровывает ограниченную порцию на сервере без открытого текстового индекса. Ни страницы, ни черновики не записываются в browser storage. Подробнее — HISTORY.md.

Браузерная QA-команда использует отдельную свежую БД, ключ и профиль, только синтетический набор; удаляет БД после завершения. В отчёте — агрегаты числа запросов/задержек/объёма, без сырых ответов API, cookie, ключей и паролей. Сами снимки синтетического UI хранятся в игнорируемом qa/browser и CI-артефакте с ограниченным сроком хранения.

## Приватное резервное восстановление, 24 октября

Реализован локальный AES-256-GCM backup с независимым случайным ключом, MVCC-снимком БД, обёрнутым ключом данных и хешированными файлами. Аутентификация всего комплекта предшествует созданию БД. Старые app_sessions исключены; SECURITY DEFINER-владельцы/ACL и RLS сохраняются и сравниваются. Восстановление поверх существующей БД запрещено, ошибка очищает только собственную новую копию. Потерянные аренды worker ограждаются, лимит попыток не сбрасывается. См. BACKUP.md. Копия и backup_key сейчас локальные; внешнее хранение/расписание/ротация этим не подключены.

Кэш приёмов теперь очищается при 401/403/404/409 через общий ресурс. Фактический браузерный сценарий проверяет отзыв и повторное включение основного согласия врача. Защита владельца и сохранность черновиков остаются отдельными проверками.
