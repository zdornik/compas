Запись на приём
==============

Работают два сценария между зарегистрированными пациентом и врачом с активным, подтверждённым пациентом подключением:

- Пациент открывает «Врач → Приёмы и запросы», выбирает врача, дату, время, длительность и формат. Запрос получает статус `requested`; время пока не бронируется.
- Врач открывает «Календарь», назначает приём подключённому пациенту (`confirmed`) либо подтверждает/отклоняет запрос пациента. Подтверждение бронирует время. Обе стороны могут отменить будущий/идущий приём; запрос пациент может отозвать.

Расписание сохраняется в PostgreSQL. Дата и время в интерфейсе — МСК (UTC+3), в API — UTC ISO 8601, в базе — timestamptz. Длительность 15–180 минут с шагом 5; создание не более чем на 366 суток вперёд. Онлайн-формат — договорённость о формате, видеосвязь не создаётся. Уведомления email/push, свободные слоты врача и перенос времени отдельным действием не реализованы.

База и права
------------

Миграция `018-appointments.sql` создаёт `public.care_appointments`, `public.care_appointment_events` и расширение PostgreSQL `btree_gist`. Индексируемые время/статус/идентификаторы хранятся как метаданные; комментарий и имена в payload, а также снимки событий зашифрованы существующим ключом данных. Runtime не может изменять/удалять историю событий или менять сохранённое время/владельца записи.

Два exclusion constraint запрещают пересечение подтверждённых интервалов как у врача, так и у пациента. Интервал полуоткрытый `[start,end)`: следующий приём можно назначить точно на время окончания предыдущего. Пересекающиеся запросы пациентов допустимы; только одно конфликтующее подтверждение сможет завершиться. Ограничения защищают и от одновременных запросов.

RLS и сервер проверяют роль, владельцев, активную связь и согласие пациента. Для видимости врачу используется существующий транзакционно обновляемый флаг `journal_access_guard.health_data`; флаги обработки/чтения заметок к приёмам не относятся. При отзыве связи или согласия healthData будущие/идущие приёмы и запросы пациента отменяются в той же транзакции, освобождая время. Пациент сохраняет свою историю; врач теряет доступ. Повторное разрешение не восстанавливает отменённые записи.

API
---

Штатные cookie, Origin, CSRF и X-Compass-Account применяются без изменений.

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/api/appointments?from=YYYY-MM-DD&to=YYYY-MM-DD&status=requested&limit=100&after=...` | Свои приёмы; даты периода по Москве, status/after необязательны; ответ `{items,nextAfter}` |
| POST | `/api/appointments` | `{id,linkId,startsAt,durationMinutes,format,note}`; format: online/in_person, note может быть пустой строкой |
| POST | `/api/appointments/:id/confirm` | Врач подтверждает запрос |
| POST | `/api/appointments/:id/decline` | Врач отклоняет запрос |
| POST | `/api/appointments/:id/cancel` | Участник отменяет запись |

Изменение требует `{expectedRevision,mutationId}`. Для одного повтора используют тот же UUID. Создание идемпотентно по id и каноническому содержимому; действия — по mutationId с записью события. Повтор возвращает актуальное состояние, не создавая второе событие. Другие данные с тем же идентификатором, устаревшая версия и занятое время дают 409. Сервер выводит статус и автора из сессии, не из тела запроса.

Проверки
--------

`npm test` включает проверки политики, времени, пагинации, авторизации API и схемы. `npm run test:appointments` запускает реальные PostgreSQL/API сценарии только при DB_NAME вида `compass_appointments_qa_<hex>` или `compass_journal_qa_<hex>` и настроенных DB_HOST/DB_PASSWORD_FILE/ADMIN_DB_PASSWORD_FILE/DATA_KEY_FILE. Используются только новые вымышленные аккаунты в отдельной базе, без чтения записей основного MVP.

Сквозные проверки покрывают оба сценария, конкурентное подтверждение, конфликты врача/пациента, соседние интервалы, точные повторы, устаревшие действия, RLS, шифрование, историю, отзыв доступа, курсоры и приём через московскую полночь. Таблицы остаются в public и не входят в экспорт справочника knowledge.
