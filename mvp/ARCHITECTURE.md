# Архитектура Компаса

Актуально на 27 октября 2026. Работающий локальный MVP для вымышленных данных. Текущая реализация описана здесь, дальнейшее развитие — в ROADMAP.md.

## Процессы

React 19.2 / Vite → один origin → Node HTTP (`scripts/serve.mjs`, `server/api.mjs`) → PostgreSQL 17. Отдельный `run-journal-worker.mjs` обрабатывает разрешённые версии заметок. Публичные PDF/изображения — в файловом архиве; текст, метаданные и поисковые индексы — в knowledge. Импорт/публикация офлайн, runtime читает справочник SELECT-only.

Основной Compose публикует только web на loopback 4174. БД в private-сети; web непривилегирован, read-only, cap_drop; архив подключён read-only. Docker runtime — Node 24. Пул API — 8 соединений, пока общий для персональных/справочных запросов; worker — отдельный пул 2.

Presentation-стенд использует отдельный нативный кластер PostgreSQL 17 на 127.0.0.1:55434 и web на 4176, собственные роли/секреты/БД/cookie. Управление — scripts/presentation.mjs, данные — игнорируемый qa/presentation. Он не требует полного корпуса и не является медицинским пилотом.

Старое внешнее демо заморожено. compose.demo.yaml применяет только миграцию 001, не запускает текущий worker и не подходит для новой сборки.

## Данные и доступ

| Группа | Назначение |
| --- | --- |
| local_patients | Технические UUID участников/владельцев, включая врачей |
| auth_accounts / app_sessions / auth_consent_events | Фиксированная роль, шифрованные профиль/согласия, scrypt, HMAC-индекс логина, хеш сессии и CSRF |
| care-сущности | Код пациента, врач, подтверждаемая связь, шифрованный аудит |
| patient_entries | Шифрованные настроение/сон/опросник/актуальная заметка/медицинский профиль/планы/отметки |
| journal-сущности / doctor_note_alerts | Неизменяемые версии, квитанции, разрешения/эпохи, задания/результаты, уведомления/аудит |
| Сообщения care | Шифрованные сообщения, принадлежность связи и курсоры |
| care_appointments / care_appointment_events | Интервалы, участники, статусы/ревизии, шифрованные детали и события |
| knowledge | Публичные источники, авторитетные факты, идентичности и производные каталоги |

AES-256-GCM, случайные IV/tag, AAD с контекстом записи/версии. Ключ отдельно от БД. Расшифровывают сервер и разрешённый worker перед отправкой клиенту: это не end-to-end. Даты/типы/связи/статусы, signal_level и другие технические поля открыты в БД. Потеря ключа означает потерю содержимого; управляемой ротации пока нет.

Пациент/врач используют отдельные HttpOnly/SameSite=Strict cookie; Secure включается для HTTPS origin. Сессионный токен в БД хеширован SHA-256. Фрагмент #doctor выбирает UI, но не права. Сервер проверяет роль, активную связь и согласие. Исследовательский вход в прежний анонимный профиль остаётся отдельным, автоматического объединения с аккаунтом нет.

Runtime — не владелец таблиц, без superuser/BYPASSRLS. app.patient_id/app.actor_id задаются на транзакцию; RLS дополняет предметную авторизацию. Origin/Host, CSRF, ограничения частоты защищают API. X-Compass-Account проверяет ожидаемого владельца, не предоставляет доступ. Смена аккаунта очищает ресурсы/черновики соответствующего кабинета, старые ответы отбрасываются.

## Заметки, приёмы и конкуренция

Связь: код → запрос врача → подтверждение пациентом. Чтение заметок, обработка текста и тестовая обработка имеют отдельные согласия. Одно подтверждение связи их не включает.

Сохранение заметки и задания — в одной транзакции. Worker получает capability через узкие SQL-функции, проверяет аренду/эпоху, сохраняет шифрованный результат. Прямого чтения персональных таблиц у worker нет. Версии, mutation ID, limited retries и lease защищают повторы/конкуренцию. Только provider stub реализован: явные TEST-маркеры выбирают тестовый сигнал, саммари — подписанный фрагмент. Реальной классификации/внешних вызовов нет. Уведомление привязано к исходной версии.

Список заметок получает версии и последние задания одним запросом с lateral join. Чтения карты/заметок используют совместные блокировки пациента/связи и выполняются параллельно; отзыв и нужные мутации используют эксклюзивные блокировки. Проверка разрешения остаётся в транзакции чтения. Блокировки не удаляются механически.

Пациент создаёт requested, врач — confirmed; врач подтверждает/отклоняет запрос, участники отменяют. Exclusion constraints PostgreSQL защищают пересечения подтверждённых интервалов обоих участников. Ревизии/квитанции защищают повторные действия. Отзыв основного согласия/связи отменяет будущие/идущие записи, сохраняет историю. Время — Europe/Moscow. Рабочих слотов, переноса, внешних напоминаний и создания видео пока нет.

Профиль/схемы/отметки лечения валидируются сервером, содержат историю и авторство. Пациент не переписывает врачебное назначение. Скрининги пересчитываются общим серверным модулем; общие модули пока находятся в src.

## Обновления UI

polling-resource.js / usePollingResource.js объединяют care/заметки по роли, владельцу, пути. Одна загрузка/таймер на ресурс, данные только в памяти; удаление при последнем отключении/смене владельца. Ошибка доступа очищает содержимое. Скрытые окна не опрашиваются; focus, возврат видимости и invalidation без PHI обновляют ресурсы. Ошибки вызывают backoff с Retry-After. Таймаут остаётся и при переданном AbortSignal.

Актуальные списки заметок/уведомлений — примерно 5 секунд, care/карта/state — 15 секунд, аккаунт — минута плюс события смены/focus. Черновики не заменяются обновлениями. State/карта получают схемы, профиль и сегодняшний день; заметки загружаются краткими страницами, исходник — при открытии, наблюдения/отметки — за выбранный период. Migration 020, HMAC-курсоры и ревизия пациента защищают перелистывание при изменениях. Подробности и границы — [HISTORY.md](HISTORY.md). Скрытые разделы врача прекращают опрос деталей заметок.

## Справочник и эксплуатация

Авторитетные факты и поисковые производные разделены, публикация транзакционная под advisory lock. Алиасы/переводы не создают медицинские соответствия, отсутствие пары не означает безопасность.

Оригиналы по SHA-256, потоковая выдача/Range/HEAD/ETag/версионное кеширование, bytea fallback. Индекс читалки публикуется офлайн; UI догружает текст рядом с областью чтения. Оригинальный PDF и fallback изображений сохраняются; runtime не переписывает клинический текст. Service worker кеширует только явную публичную статику, персональные API no-store.

Справочный export v2 включает БД и объекты; опубликованный v1 около 15,9 ГБ, полная загрузка отложена. Основной локальный набор — одна КР 301_3, 125 страниц и 25 изображений; препаратов/взаимодействий нет. Presentation-пакет может переносить только этот образец с хешами. Персональные таблицы/секреты не входят в справочные пакеты.

CI: сборка, Node/Python, четыре PostgreSQL/API-сценария и браузерный smoke с Playwright на свежей изолированной БД. check-integration.mjs создаёт свой ключ/БД, применяет схему и удаляет свою БД. Presentation preflight проверяет процессы, выполнение пробного задания, миграции и staged-файлы образца. Открытый /api/health остаётся простой проверкой БД, а не диагностикой продукта.

Остаются длительная репетиция/нагрузка, оптимизация больших архивов схем, полный API-контракт, операционные метрики, управление ключами, вынос/расписание/хранение приватных бэкапов, проверенная идентификация, реальный провайдер и экспертная оценка качества. См. SECURITY.md и ROADMAP.md.

## Приватное восстановление и проверка показа

BACKUP.md описывает AES-GCM-комплект согласованного MVCC-снимка, ключа данных и файлов; внешний backup_key хранится отдельно. Старые сессии не восстанавливаются, владельцы SQL-функций сохраняются, потерянные worker-токены ограждаются. Проверки работают только в новых отдельных БД; существующая цель запрещена. Это реализованный локальный механизм небольшого стенда, не настроенная внешняя резервная служба.

Подготовка разных QA-БД использует общий advisory lock в postgres для изменений кластерных ролей; пароли проверяются повторно внутри блокировки. Календарь переведён на общий ресурс с отменой/очисткой при отказе в доступе. Длительный прогон и резервное видео запускаются отдельно от обычного CI; исходные данные только синтетические.
