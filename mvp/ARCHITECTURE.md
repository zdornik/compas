# Архитектура Компаса

## Сейчас: проверка интерфейса

Браузер → React 19.2 → состояние в памяти страницы. Vite 6.4.4 собирает статические файлы. Phosphor даёт единый набор иконок. CSS-токены управляют тремя цветовыми состояниями; растровые сцены переключаются через opacity, без анимации раскладки. Клиентские часы форматируются в Europe/Moscow для этой демоверсии.

Выбран web-шаблон Product Design, поскольку запрошен сайт с десктопным видом и возможностью установки, а не эмулятор мобильного устройства. Браузерная клавиатура и нативные HTML-поля работают напрямую. При ширине до 760px — мобильная компоновка и нижняя панель; выше — боковая навигация. Основной экран повторяет v7, остальные экраны используют тот же цвет, отступы, символы и поверхности.

Нет backend, авторизации, API, постоянного хранилища, медицинской аналитики или отправки данных. Установленная PWA остаётся демоверсией. Отсутствие backend на данном этапе уменьшает поверхность утечки, но не является реализацией защиты клинической системы.

## Следующая итерация: модульный монолит

Браузер/PWA → один HTTPS origin и reverse proxy → FastAPI → PostgreSQL. Статический frontend оставить отдельной сборкой, API разместить под /api. Один репозиторий, один API и одна БД достаточны для MVP; микросервисы, отдельная поисковая инфраструктура и векторная БД пока не нужны.

- Frontend: при подключении API добавить TypeScript и валидацию контрактов; формы и запросы типизировать. Переход к SSR не нужен для закрытого кабинета без SEO.
- API: FastAPI, Pydantic, SQLAlchemy и Alembic. Конкретные поддерживаемые версии выбрать и зафиксировать при создании backend.
- БД: PostgreSQL, проверки ограничений и транзакции; RLS дополнительно к проверкам API. Runtime-роль не superuser и не владелец таблиц.
- Identity: проверенный компонент OIDC или mature session library; серверные сессии в HttpOnly cookie. MFA врача, отзыв и аудит.
- Фоновые задачи: сначала одна очередь/worker для плановых напоминаний и повторов. Redis/Celery добавлять при подтверждённой необходимости, не запускать второй контур только ради демо.
- Вложения: закрытое объектное хранилище, ограниченные по времени ссылки после проверки прав; антивирус, лимиты и типы файлов до подключения загрузок.
- Мониторинг: технические метрики и аудит без содержания дневников. Никакого session replay на медицинских экранах.

Расположение серверов, резервных копий и подрядчиков выбрать под фактическую юрисдикцию и документы оператора до ввода реальных данных. Соответствие нельзя подтвердить выбором стека или одним шифрованием.

## Минимальные сущности

| Сущность | Назначение и важное ограничение |
|---|---|
| User / Patient / Clinician | Идентификатор входа отдельно от медицинского профиля |
| CareRelationship | Врач, пациент, период доступа, статус и ссылка на согласие |
| Consent | Цель и версия согласия, выдача/отзыв, аудит |
| MoodEntry | Пациент, время/часовой пояс, момент/день, значение, слова, факторы, заметка |
| SleepEntry | Дата сна, длительность, качество, источник ручной/интеграция |
| MedicationPlan / DoseSchedule | Назначение с автором и историей; титрация только по подтверждённому плану |
| DoseEvent | Конкретная плановая доза, факт/пропуск, время, idempotency key |
| QuestionnaireAssignment / Response | Версия инструмента, автор назначения, срок, ответы; расчёт по проверенному алгоритму |
| Appointment | Пациент, врач, дата/часовой пояс, статус и источник подтверждения |
| Conversation / Message | Участники, доступ, доставка и политика хранения |
| PushSubscription | Владелец, согласие, зашифрованные ключи, отзыв |
| AuditEvent | Кто и к каким данным обращался, без содержимого записей |

Каждая запись принадлежит конкретному пациенту; owner_id нельзя брать на доверии из клиентского JSON. Удаление/исправление назначения и клинические изменения должны быть версионированы. Для пацента без активного врача личный дневник и право доступа врача — разные состояния.

## API-порядок реализации

1. /session и /me с серверной идентификацией.
2. /mood-entries и /sleep-entries с пагинацией и авторизацией.
3. /medication-plans и /dose-events с врачебными правами, идемпотентностью и аудитом.
4. /questionnaire-assignments и /responses с версией инструмента.
5. Отношения врач–пациент, календарь и защищённая переписка.
6. Push-подписки, очередь и нейтральные тексты напоминаний.

Это проект контрактов, а не существующие endpoints. Сейчас приложение не отправляет к ним запросы.

## Развёртывание

Для демо достаточно статического frontend за TLS. `scripts/serve.mjs` запускает собранные файлы и выставляет защитные заголовки. Dockerfile запускает runtime от пользователя node; порт наружу должен вести только через reverse proxy. Файл Caddyfile.example показывает HTTPS-домен. Образы при реальном выпуске фиксировать по digest и обновлять по процессу CI.

Для защищённого MVP: один origin, API в приватной сети, PostgreSQL без публичного доступа, backup в согласованном регионе, ключи отдельно от данных, staging только с синтетическими примерами. До первого пациента требуется завершение P0 из TASKS.md, проверка восстановления и независимая проверка безопасности.

## Пока сознательно не подключено

LLM, pgvector, RAG, медицинские рекомендации и лекарственные взаимодействия. Нет проверенного корпуса, источников, клинической оценки и согласованного контура обработки. Их интерфейс не должен выглядеть работающим. Будущая LLM выдаёт только проект сводки со ссылками на исходные записи, который проверяет врач; не назначает лечение.
